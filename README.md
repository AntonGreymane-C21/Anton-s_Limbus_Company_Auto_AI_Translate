## 二、术语与译名来源

汉化的可用性，很大程度取决于术语一致性。本项目在术语层面**参考并采用了「零协会」的公开术语库译法**，在此基础上维护 `config/glossary.json`：

- 当前术语库共 **94** 条，其中大部分为 `locked: true`（强制术语，AI 不得自行改动译名）；
- 术语库同时用于**提示词注入**与**译文校验**（`TerminologyValidator` 会检查锁定译名是否被正确使用）；
- 未收录词条在提示词中明确要求：**优先采用边狱巴士中文社区的通译，不得自行造词**（见 `config/prompt.json`）。

**在此感谢「零协会」及社区译者的整理与贡献。** 若涉及译名归属、署名方式或使用范围需要调整，请与作者联系，会及时修改或移除。

## 三、核心能力

### 3.1 四种翻译模式

游戏官方以韩文为原文，英文与日文属于不同语言的官方文本。历史上多数工具只依据英文翻译，会丢失韩文语义。本项目提供四种模式：

| 模式名称 | 配置码 | 权威原文 | 参考译本 | 适用场景 |
|---|---|---|---|---|
| 英文翻译 | `en_only` | 官方英文 | 无 | 兼容既有英文流程与历史翻译记忆，Token 消耗最低 |
| 韩文原文 + 英文参考 | `kr_en` | 韩文 | 英文 | 推荐默认：语义以韩文为准，措辞参考英文 |
| 韩文原文 + 日文参考 | `kr_jp` | 韩文 | 日文 | 需要日文语感或叙事风格参考时使用 |
| 仅韩文原文 | `kr_only` | 韩文 | 无 | 完全依据韩文翻译，自动启用深度推理，Token 消耗较高 |

模式语义（唯一由后端决定，界面只做展示）：

- 韩文原文发生变化 → 必须重新翻译，即使英文没有任何改动；
- 仅英文或日文参考文本变化 → **不视为源文变化**，不会触发重新翻译；
- 韩文中存在、英文中缺失的条目 → 依然能够翻译并输出，不会被英文结构过滤掉；
- 韩文中已删除的条目 → 不会因为英文仍存在而重新出现在汉化中。

### 3.2 工程能力

| 能力 | 说明 |
|---|---|
| 版本差异分析 | 文件级 + 条目级 Diff，区分新增 / 修改 / 缺失译文 / 可继承 / 已删除 |
| 翻译记忆（TM） | SQLite 精确命中（UnitKey + SourceHash），命中即复用，不产生 API 消耗；四模式通过模式盐互相隔离 |
| 请求缓存 | 基于请求指纹（v3）缓存模型响应，同模式同请求直接复用 |
| 术语库 | 锁定 / 优先两级语义，动态子集注入提示词，并与校验共用同一匹配实现 |
| 校验体系 | 默认 13 条规则（空译、占位符、数字、标签、换行、英文残留、韩文残留、日文假名残留、长度异常、术语不一致、源语言异常、缺少韩文原文等），问题描述均已中文化 |
| 人工审核 | 待审核列表、筛选、搜索、逐条审校；支持修改译文并写回翻译记忆（来源标记为「人工审核」） |
| 输出合并 | 以权威结构为模板写回 JSON（英文模式 = 英文结构；韩文模式 = 韩文结构），并保留非翻译字段与格式 |
| 发布门禁 | 检查缺失 Key、非预期 Key、结构错误、待审核项，输出「检查通过 / 需要人工确认 / 存在阻塞问题」 |
| 事务式部署 | 备份 → 替换 → 失败回滚；回滚不完整时明确标记高危并列出未恢复文件；必须人工确认 |
| 运行诊断 | 阶段耗时、线程归属、Token 统计、Agent 决策与模型自报「建议人工确认」均可追溯 |

## 六、使用流程（图形界面）

1. **指定目录**
   - 新版英文：当前游戏 `LimbusCompany_Data\Assets\Resources_moved\Localize\en`
   - 旧英文：上一版本的 `Localize\en`（用于计算英文差异并提供结构参考）
   - 旧中文：已有的汉化目录（例如 `LimbusCompany_Data\Lang\LLC_zh-CN`）
   - 可在界面点「自动定位游戏」，或手动填写 / 浏览选择
2. **配置 API**：在「配置」窗口填写 DeepSeek API Key（密钥以密码方式输入，界面不明文回显），点击「测试连接」确认可用
3. **选择翻译模式**：推荐「韩文原文 + 英文参考」
4. **分析更新**：点击「分析更新」，查看新增 / 修改 / 缺失译文 / 可继承 / 需审核等统计
5. **开始翻译**：点击「开始汉化」，界面实时显示阶段、进度、当前文件、TM / 缓存命中与警告
6. **人工审核**：在「待审核」页筛选、搜索、逐条校对；可修改译文并保存（写回翻译记忆，下次直接命中）
7. **生成输出**：点击「审核后重新输出」，随后进行发布门禁检查
8. **部署（可选）**：点击「部署到游戏」，在确认框中核对目标目录、文件数与备份 / 回滚说明后确认

> 演示与试跑：执行 `dotnet run --project .\src\LimbusTranslator.Cli -- --gui-demo-workspace` 会在系统临时目录生成一份演示工作区（覆盖新增 / 修改 / 继承 / 缺失译文 / 含韩文残留 / StoryData 邻句六类场景），并按提示输出可填入界面的三个目录。该过程不读取游戏目录、不调用 API、不影响生产数据。

## 九、工作流程（技术说明）

```
Localize/{en,kr,jp}
   │  扫描与解析（真实数据：6311 个 JSON，约 44.7 万条 TranslationUnit）
   ▼
三语快照 + Canonical Diff（以韩文为准；英文 / 日文仅用于参考译本变化诊断）
   ▼
生产翻译计划（唯一事实来源）
   · 候选：韩文模式 = 当前韩文 Key 集；英文模式 = 英文 Diff 结构
   · ApplyToEntries：决定最终动作（新增 / 修改 / 缺失译文 / 继承 / 忽略删除）
   · 按最终动作过滤：只有真正需要翻译的条目进入 Agent
   ▼
Coordinator / TranslationAgent
   · 翻译记忆精确命中 → 直接复用
   · 请求缓存命中 → 复用模型响应
   · 否则调用 DeepSeek 批量翻译（占位符保护、响应校验、重试、宽容恢复）
   ▼
校验（13 条规则）→ 人工审核（可选）→ 合并输出（权威结构模板）
   ▼
发布门禁（缺失 / 非预期 Key、结构错误、待审核）→ 部署（可选，事务式，需人工确认）
```

**执行与性能**

- 分析、翻译等重任务全部在后台线程执行，界面保持可响应；
- 进度上报按约 150 ms 节流，不逐条刷新界面；
- 分析过程可随时取消：取消不写入快照、不改变统计、不产生半成品输出；
- 三语快照采用事务式提交（准备 → 提交 → 失败回滚），不会出现部分语言已更新的中间状态；
- 实测（6311 文件 / 44.7 万条单元）：完整分析约 13.6 秒。

## 十三、常见问题

**Q：没有 API Key 能否使用？**
可以完成分析、继承旧译文、翻译记忆与缓存命中、合并输出与发布检查；只有确实需要翻译的新文本需要 API。

**Q：为什么有些条目没有被翻译？**
这些条目本身不需要翻译：韩文原文未变化（继承旧中文）、仅参考文本变化、韩文已删除该条目，或已命中翻译记忆 / 请求缓存。

**Q：如何降低 Token 消耗？**
优先使用 `kr_en` 模式；适当调大批处理条数（`batch.maxItemsPerBatch`）；保持翻译记忆与请求缓存不被清空；完善 `glossary.json` 术语表可减少模型在译名上的推理量。

**Q：出现「韩文残留」「日文假名残留」等提示怎么办？**
属于校验的启发式警告，不是错误。通常是模型带出了原文片段，在审核页修改即可；若属术语问题，可将术语加入 `glossary.json` 并标记为锁定。

**Q：Paratranz 同步失败或返回 403？**
Paratranz 属于可选功能，失败仅影响远程术语同步，不影响本地术语表、翻译、审核与输出。

**Q：能否只处理部分内容？**
可以。在「任务范围」页按分类勾选需要处理的范围（StoryData、技能、物品等）。

**Q：工具会修改游戏文件吗？**
除用户在确认框中明确同意的部署操作外，其余流程对游戏目录只读。

**Q：支持非 Windows 平台吗？**
命令行部分基于 .NET，理论上可跨平台运行；图形界面为 WPF，仅支持 Windows。
